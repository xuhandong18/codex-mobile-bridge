# Codex 容量错误自动继续

网关设置的「应用与维护 → 常规」提供「Codex 容量错误自动继续」，默认开启。保存后最多 3 秒生效，不用重新启动网关。关闭手机网页和通知通道不影响后台监督。

## 哪些聊天会被处理

网关复用聊天状态和只读元数据发现，覆盖可访问的本机、已配置 SSH 主机上的 Codex 主聊天。每 30 秒增量发现新增或更新的聊天，已有连接的状态变化直接交给监督器。初始探测分批进行；空闲聊天释放监督器自己的订阅，运行中和正在恢复的聊天继续保留。通知、活动状态查询和手机阅读的订阅独立保留。

每个聊天首次成功同步状态时建立基线，已有失败不自动恢复。之后的新失败轮次，或者已经观察到正在运行的一轮变为失败，才可能触发。首次尚未同步到运行状态就已经失败的聊天也只记基线，避免把旧任务误当成新错误。改名、已读变化、重新连接、重新开启开关不会重新启动旧失败。

必须同时满足最新一轮为 `failed`、当前没有运行任务或待确认请求，并且该轮结构化错误的 `codexErrorInfo` 为 `serverOverloaded`。只有缺少错误码时，才严格匹配以下完整文案：

```text
Selected model is at capacity. Please try a different model.
```

聊天列表橙点也可能表示手动停止或未读结束，因此不作为自动恢复依据。其他错误、正文中引用的错误 JSON、子代理、侧边聊天、Claude 和 DeepSeek 不参与自动继续。

## 发送与三次上限

首次匹配到新容量错误，立即向原聊天发送 `继续执行`。若这次自动消息产生的新一轮仍报容量错误，从确认失败开始再等 10 分钟。同一次连续故障最多自动发送 3 次；自动消息被接受或短暂恢复运行不会重置计数。三次都失败后保留失败状态，网关运行日志记录「已达三次，需人工处理」。正常完成结束本次恢复，人工新发的任务可以建立新的恢复周期。

每次发送前重新向原 owner 请求实时快照，并在操作锁内核对聊天、轮次、owner、工作目录、provider、运行状态、人工请求和待发消息。人工发送、停止、切换 owner 或已有更新任务会取消旧的待发计划。新轮次的用户消息身份可能稍后到达，监督器会等待可核验的关联；最终仍无法关联时停止自动处理，避免把自动消息当作人工新任务重置次数。

续跑继承原模型、权限和工作模式，不调用桌面激活、打开聊天或冷恢复入口，不启动第二个运行时。原 owner 暂不可用时只等连接恢复。提交前先持久保存计数、唯一提交 ID 和未知状态；发送断连、超时或回执丢失后停止自动处理，不能自动补发。

## 设置、存储与生命周期

桌面设置读取/保存接口使用 `codexRecovery: {enabled: boolean}`。设置保存在网关数据目录的 `codex-recovery.json`，恢复记录保存在 `codex-recovery-ledger.json`，消息回执复用 `submissions.json`。写入使用独占临时文件、文件提交和原子替换；记录不保存聊天正文。

监督器只由网关启动入口创建；桌面管理进程临时创建的服务实例不会自动续跑。主机身份和原生操作沿用现有客户端归属与账号操作门。关闭开关取消未发送的恢复任务，重新开启和网关重启建立新基线；旧提交和计数保留，未知结果不重放。退出网关时先停止监督器，再关闭客户端连接。

日志只包含主机、聊天、轮次、次数和原因，不包含聊天正文或认证信息。配置读取失败时停止自动处理。

## 验证

```sh
python -B scripts/test-backend.py --source-only -p test_codex_recovery.py
python -B scripts/test-backend.py --source-only -p test_desktop.py
python -B scripts/test-backend.py --source-only
npm run test:desktop
node scripts/test-codex-recovery-browser.cjs
```

浏览器驱动需要已有 Playwright/Chromium，可通过 `NODE_PATH`、`BROWSER_EXECUTABLE` 指定。驱动执行真实桌面布局、设置收集、保存和重载流程，控制器由隔离绑定模拟；覆盖默认开启、运行中保存、重新加载、重新开启、中英文和较小桌面窗口。可加 `--screenshots` 将截图保存在 `.tmp/`。

所有测试使用合成状态、可控时钟和模拟 owner，不向真实聊天发送消息。源码及浏览器测试不代表已构建、安装或完成真实客户端联调。
